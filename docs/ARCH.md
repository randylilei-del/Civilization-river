# 架构：数据迁出 HTML（2026-08-09 定，Ray 拍板）

## 一句话总结

这个项目不是「前端代码臃肿」，而是**一个 1.5 MB、45 张表、经过重度核查的历史数据集，
物理上住在一个 HTML 文件的 `<script>` 标签里**。要治的是数据的住处，不是代码架构。

体检数字（2026-08，v110 时点）：index.html 磁盘 2.3 MB，其中数据约 93%、
渲染+交互 JS 76 KB（4%）、CSS 29 KB（1%）。渲染器是健康的，**不做** React 化、
组件化、CSS 拆分。

## 要解决的三个真实病灶（都咬过人，见 HANDOFF「试过但失败的路」）

1. **数据没有机器可读的正本**——`tools/audit.js` 靠字符串切片从 HTML 抠数据段，
   `AGLYPH` 在 `TRACES` 之后要单独补一段，「再往后加新表要记得同样处理」是已知陷阱：
   新表位置不对会被 audit **静默漏掉**。
2. **中英平行字典靠索引对齐**——好几条 audit 规则专职盯数量一致，这类错误本该由结构杜绝。
3. **编辑工学**——2.3 MB 单文件里做锚点替换；python 批量脚本 assert 失败整批丢失的事故
   发生过一次。

## 目标架构

```
改数据:  data/<表名>.js ──┐
                          ├─ node tools/build.js ─→ index.html（commit + 部署，照旧）
改代码:  index.html 直接改 ─┘                          ↑
                                     audit 规则 45: 重建比对，漂移即报
```

- **运行时铁律全部保留**：单文件交付、离线可用、零外部请求。给孩子的产品一个字节不变。
- **放弃的只有「无构建」半句**：改数据要跑一次 `node tools/build.js`。
- **产物照旧 commit**：Vercel / EdgeOne 零配置，部署链路不变。

### 关键决策与理由

| 决策 | 选了什么 | 为什么不选备选 |
|---|---|---|
| 数据格式 | **`.js` 文本片段**（内容就是原样的 `const X = {…};`） | JSON 没有注释——v109 那批 Taagepera 溯源注释是两年吵出来的口径，不能杀；且 `.js` 原文剪切可保 byte 级一致，JSON 重新序列化做不到；YAML 要引依赖，违反红线 |
| 注入方式 | **原地标记区间**（`/*__DATA:<name>:start__*/ … end`，标记本身是合法 JS 注释） | template 方案会让仓库躺两个 1.6 MB 近似文件，且改代码的工作流也得变；原地标记下 index.html 任何时刻都完整可运行，不存在坏的中间态 |
| 迁移单位 | **按表**，一次一张 | 数据按表组织（列存），按文明切会让每张表出现双数据源 |
| audit 读取 | 迁移期间照旧读 index.html（内容逐字节相同）；**全部迁完后**改为按目录枚举 `data/*.js`，切片 hack 自然消失 | 提前切换 = 一次大手术，违背渐进原则 |
| 数据库 | **不用**。JSON/SQLite/Supabase 都不引入 | 单写者、静态、离线、零查询需求；git 就是审计日志。触发条件（多写者/第二消费端/内容 10x）出现前不回访这个问题 |

### One History, Many Lenses 的处理（Ray 保留的设计原则）

**不实现任何 lens 机制**。它以纪律的形式存在：

- fact 类表（年份/坐标/版图/硬数字）保持受众无关——现状已是如此，守住即可；
- 新增 fact 字段不得掺叙事语言；新增叙事内容不得混入 fact 表；
- 各表性质（fact / interpretation / presentation / config）标注在 DATA.md，
  **config 类（渲染参数）永远不迁移**。

理由（讨论中确认）：这个项目最贵的是「写出来并核实过的句子」，不是数据结构。
未来若真出现第二受众，叙事层是重写不是重渲染，schema 救不了；而 fact 层今天已经安全。

### 唐朝 prototype 是另一条线

产品实验（验证 7 岁孩子的认知路径），与本迁移完全解耦，不承担任何重构任务，
不往 index.html 写东西。用现有数据在旁边搭原型页。

## 分阶段路线

- **Phase 1**（本次）：迁 `PEAK` 一张表，建立 `data/`、`tools/build.js`、audit 规则 45。
  产物与迁移前差异精确 = 两行标记注释。
- **Phase 2**：逐表机械搬迁（纯移动，零 schema 变更）。顺序从小而稳的表开始
  （VIDEO/EVENTS/TRACES → GEO/CHRONO/GL → LAND/BORDERS → PLACE_LORE/PEOPLE/ACHV → CIVS/EN 最后）。
  内容表约 25 张；渲染参数类 const 不迁。
- **Phase 3**：全部迁完后，audit 改读 `data/` 目录，删除 HTML 切片逻辑。
- **Phase 4**（独立决策，可不做）：按表把中英平行字典合并为 `{zh,en}` 成对结构——
  唯一值得做的 schema 变更，把索引错位类错误由构造杜绝。**动渲染器，一张表一张表来。**
- **到此为止**。不做 Knowledge 层结构化 schema、不做 lens engine、不做数据库。

## 成功标准（Ray 确认的六条）

1. 用户看到和使用的产品与重构前一致；
2. audit 不再依赖 HTML 提取 hack（Phase 3 兑现）；
3. 改一条历史内容时，diff 基本只发生在 `/data`（产物区间的再生成 diff 除外）；
4. build 确定且可验证，生成物与正本不得漂移（规则 45 守卫）;
5. 中英对齐等已知错误尽可能由结构杜绝（Phase 4 兑现）;
6. 渲染器和部署链路没有变复杂。

四条硬标准有一条不满足，就是白拆。

## 回滚

每个 Phase 单 commit 原子提交。`git revert` 即整体回滚；因为部署产物始终是
完整自洽的 index.html，任何中间态站点行为都不受影响。

## 给下一个会话的操作提醒

- 改**已迁移**的表：改 `data/<表名>.js` → `node tools/build.js` → 后续验证照旧。
  **直接改 index.html 里的数据区间是错的**，audit 规则 45 会拦。
- 改**未迁移**的表和所有代码：照旧直接改 index.html。
- 迁移新表的手法照 Phase 1：原文剪切（含表头注释）→ 加标记对 → build 幂等验证 →
  git diff 只多两行标记。
